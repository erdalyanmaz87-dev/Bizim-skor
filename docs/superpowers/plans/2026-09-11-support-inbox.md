# Support Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Oyuncuların uygulama içinden destek talebi göndermesini, yöneticinin bu talepleri okuyup cevaplamasını ve oyuncuların yanıtları rozetli şekilde görmesini sağlamak.

**Architecture:** Yeni bir `support_requests` tablosu ve güvenli RPC katmanı eklenecek. Oyuncu tarafı mevcut doğrulanmış oyuncu tokenını kullanacak; yönetici tarafı ise normal oyuncu adından bağımsız, sunucu tarafında doğrulanan yönetici oturumuna bağlı RPC’lerle çalışacak. Arayüz iki odaklı dosyaya ayrılacak: oyuncu destek deneyimi ve yönetici gelen kutusu.

**Tech Stack:** Vanilla JavaScript, HTML/CSS, Supabase PostgreSQL + PL/pgSQL RPC, Node test runner.

**Spec:** `docs/superpowers/specs/2026-09-11-support-inbox-design.md`

## Global Constraints

- Geliştirme yalnızca `feature/support-inbox-v1` dalında yapılacak.
- Production/main kullanıcı onayı olmadan değiştirilmeyecek.
- Mesaj uzunluğu en fazla 500 karakter olacak.
- Kategoriler yalnızca: `login_pin`, `predictions`, `points_ranking`, `technical`, `suggestion`, `other`.
- Durumlar yalnızca: `new`, `answered`, `resolved`.
- İlk sürümde dosya/fotoğraf eki ve WhatsApp tarzı sürekli sohbet olmayacak.
- Oyuncu yalnızca kendi taleplerini görebilecek.
- Yönetici yetkisi istemci tarafındaki oyuncu adına veya `is_admin` benzeri bir parametreye güvenmeyecek.

- [ ] **Step 3: Implement minimal utility module**

```js
const CATEGORIES=new Set(['login_pin','predictions','points_ranking','technical','suggestion','other']);
function normalizeSupportCategory(value){return String(value||'').trim().toLowerCase()}
function validateSupportMessage({category,message}){
  const cleanCategory=normalizeSupportCategory(category),cleanMessage=String(message||'').trim();
  if(!CATEGORIES.has(cleanCategory))return{ok:false,message:'Geçerli bir kategori seçin.'};
  if(!cleanMessage)return{ok:false,message:'Mesajınızı yazın.'};
  if(cleanMessage.length>500)return{ok:false,message:'Mesaj en fazla 500 karakter olabilir.'};
  return{ok:true,category:cleanCategory,message:cleanMessage};
}
function hasUnreadAdminReply(row){return Boolean(row?.admin_reply&&row?.answered_at&&!row?.player_seen_reply_at)}
module.exports={CATEGORIES,normalizeSupportCategory,validateSupportMessage,hasUnreadAdminReply};
```

- [ ] **Step 4: Write migration with table constraints**

```sql
create table public.support_requests (
  id bigint generated by default as identity primary key,
  player_name text not null,
  category text not null check (category in ('login_pin','predictions','points_ranking','technical','suggestion','other')),
  message text not null check (char_length(message) between 1 and 500),
  status text not null default 'new' check (status in ('new','answered','resolved')),
  admin_reply text,
  created_at timestamptz not null default now(),
  answered_at timestamptz,
  resolved_at timestamptz,
  player_seen_reply_at timestamptz
);

alter table public.support_requests enable row level security;
revoke all on public.support_requests from anon, authenticated;
```

Use the existing friend/session token validation pattern in the repository to resolve `p_token` to an active player inside all player RPCs. Never accept `player_name` directly from the client for ownership.

- [ ] **Step 5: Add `create_support_request`**

RPC requirements:
- resolve player from `p_token`,
- reject invalid category,
- trim message,
- reject blank or >500 characters,
- insert `player_name` from verified token,
- return new request ID.

- [ ] **Step 6: Add `list_my_support_requests`**

Return columns in this order:
`id, category, message, status, admin_reply, created_at, answered_at, resolved_at, player_seen_reply_at`.
Only rows owned by the verified token’s player are returned, newest first.

- [ ] **Step 7: Add `mark_support_reply_seen`**

Update `player_seen_reply_at=now()` only where `id=p_request_id` and request owner matches the verified token player.
